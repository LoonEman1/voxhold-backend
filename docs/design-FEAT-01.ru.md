# Дизайн FEAT-01: входящие вебхуки каналов

Статус: черновик, **нужно решение владельца по хранению автора** (см. ниже).

## Предложение

- `channel_webhooks(id, channel_id, name, token_hash, created_by, created_at)`; токен показывается
  один раз, хранится SHA-256.
- Управление (owner/admin): `POST/GET/DELETE /api/v1/servers/{id}/channels/{cid}/webhooks`.
- Публичный `POST /api/v1/webhooks/{id}/{token}` с телом `{"content": "...", "username": "..."}`
  (до 5120 символов). Совместим по полям `content` и `username` с Discord-вебхуками.
- Отдельный лимит по вебхуку (5 запросов в секунду), без упоминаний ролей (SEC-04), без вложений
  в первой версии.

## Как хранить автора сообщения (нужно решить)

1. **Служебный пользователь на вебхук.** Создаётся строка `users` с флагом `is_webhook`, пустым
   `password_hash` (вход невозможен) и членством в сервере. Плюс: ничего не меняется в таблице
   `messages` и во всех запросах. Минус: «пользователи» в списках участников, нужно их скрывать;
   удаление вебхука должно анонимизировать пользователя.
2. **Колонка `messages.webhook_id`** и автор — создатель вебхука либо NULL. Плюс: чистая модель.
   Минус: `author_user_id NOT NULL` и внешние ключи, много запросов читают автора join-ом; нужна
   миграция таблицы и правка всех выборок.

Рекомендация: вариант 1 на первой версии (меньше риска), с флагом, который скрывает такого
пользователя из списков и запрещает вход, ЛС и голос.

## Риски

Токен в URL виден в логах прокси; ограничить срок и дать пересоздание. Спам через утёкший токен:
лимит и быстрое удаление. Нужен тест, что вебхук не может писать в другой канал.
