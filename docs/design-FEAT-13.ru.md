# Дизайн FEAT-13: сквозное шифрование голоса

Статус: **черновик на утверждение владельцем. Код не пишется до одобрения.**
Область: только голос (голосовые каналы и звонки в ЛС). Видео и звук стримов не шифруются.
Запись звонков остаётся разрешённой.

## Цель и модель угроз

Сервер (SFU `internal/voice`) не должен мочь прослушать голос.

Защищает от: прослушивания сервером, утечки дампа памяти или трафика SFU, администратора хоста,
который только смотрит трафик.

Не защищает от: активно вредоносного сервера, подменяющего публичные ключи (без сверки кодов
безопасности); метаданных (кто, с кем, когда, объём); записей (хранятся на сервере открыто,
интерфейс об этом предупреждает); видео и стримов; текстовых сообщений.

Формулировка в интерфейсе: «Голос зашифрован сквозным шифрованием: сервер не может его
расшифровать. Сверьте коды безопасности, чтобы исключить подмену ключей». Слова «полная защита» не
используются.

## Архитектура

- Ключи устройства: ECDH P-256, приватный ключ неизвлекаемый (`extractable: false`) в IndexedDB,
  публичный регистрируется на сервере (`e2ee_device_keys`, не более 10 активных устройств).
- Схема «ключ отправителя»: каждый участник шифрует свои кадры случайным AES-256-ключом и раздаёт
  его остальным, зашифровав для каждого устройства (ключ обёртки: HKDF-SHA-256 от ECDH,
  AES-GCM с AAD). Сервер пересылает событие `e2ee.key` только соединениям получателя и не читает
  `payload`.
- Ротация ключа при любом изменении состава комнаты (с дебаунсом 2 с) и каждые 10 минут;
  `key_id` 0–7 по кругу.
- Кадры: шифруется только Opus. Формат `[TOC 1 байт открыто][заголовок 1–3 байта в стиле SFrame]
  [шифротекст][тег 16 байт]`, AES-GCM 256, IV = соль XOR CTR. Накладные расходы ≈ 19 байт на
  кадр (≈ +7,6 кбит/с). Защита от повторов окном из 128 значений CTR.
- Трансформация в Web Worker: `RTCRtpScriptTransform`, а в Chrome — `encodedInsertableStreams`
  (через все sender/receiver соединения; видео демонстрации в звонке пропускается без изменений).
- Политика: `channels.e2ee_required`; сервер не пускает в такой канал клиента без
  `e2ee_device_id`. Код безопасности (SHA-256 от пар ключей, 60 цифр) и TOFU-предупреждение
  при смене ключа.

## API и миграции

1. `e2ee_device_keys(user_id, device_id, public_key, created_at, revoked_at)`, уникально
   `(user_id, device_id)`.
2. `PUT/DELETE /api/v1/me/e2ee/devices/{deviceID}`, `GET /api/v1/users/{id}/e2ee/devices`.
3. WS: `e2ee.key`, `e2ee.key_request`; в `voice.join` поле `e2ee_device_id`.
4. `channels.e2ee_required INTEGER NOT NULL DEFAULT 0`.

## Этапы (каждый — отдельный PR; этапы 2 и 3 нужно отдавать на ревью более сильной модели или человеку)

1. Ключи устройств (frontend + backend).
2. Раздача ключей отправителя (backend пересылает, frontend шифрует ключи).
3. Шифрование аудиокадров (Worker), производительность закладывается сразу.
4. Политика и интерфейс (замок, плашки, код безопасности, пометка про записи и стримы).
5. Проверки: тесты воркера, заголовка (CTR 0, 7, 8, 255, 256, 65535, 65536), накладных расходов,
   склейки ротаций, пересылки `e2ee.key`; Playwright на Chromium и Firefox, замер задержки
   (> 5 мс на кадр — остановиться и сообщить).

## Риски и открытые вопросы

- Ошибка в криптографии не видна по принципу «звук идёт». Использовать только WebCrypto и
  стандартную библиотеку Go; никаких самописных примитивов; пару (ключ, IV) не повторять.
- Safari: есть ли `RTCRtpScriptTransform` на нужных версиях — проверить; при отсутствии клиент
  явно сообщает, что E2EE недоступно.
- Нагрузка рассылки ключей при входе большого числа участников — лимит WS (burst 60); при
  необходимости разносить по времени.
- Нужен ли MLS — отдельное решение владельца после первой версии.
