# Новостные каналы и счётчики уведомлений

Перед запуском нового backend применяются миграции **000025** и **000026**.
Обновляется также соседний `Voxhold-frontend`. Рабочая база автоматически этим
изменением не мигрировалась.

## Каналы и права

`POST /api/v1/servers/{serverID}/channels` принимает `kind: "news"`.
В API это третий самостоятельный вид канала. В SQLite он хранится как текстовый
канал с `is_news=1`: это сохраняет существующие FK, FTS, записи, read cursors,
ACL и историю без пересоздания таблицы `channels`.

Владелец и администраторы сервера могут публиковать всегда. Дополнительные авторы
назначаются индивидуально. Для закрытого канала **автору также нужен обычный ACL**:
назначение автором не предоставляет доступ к приватной истории. Читатель может
читать, ставить реакции и, когда разрешено, отправлять комментарии. Прямая отправка,
пересылка в ленту и редактирование публикаций проверяют право публикации в транзакции.
После отзыва права автора редактирование поста запрещается; удалить собственный
контент он может при сохранённом доступе к каналу.

Настройки доступны только менеджерам сервера:

```http
GET /api/v1/servers/{serverID}/channels/{channelID}/news
PUT /api/v1/servers/{serverID}/channels/{channelID}/news
```

```json
{"publisher_ids":[12,34],"comments_enabled":true}
```

`comments_enabled` обязательно для PUT. Идентификаторы должны принадлежать текущим
участникам этого сервера; допускается до 1000 авторов. Настройки по умолчанию:
авторы — владелец/администраторы, комментарии выключены. Изменения вызывают
`channels.changed`; клиенты обновляют персональные `can_publish` и `comments_enabled`.
Обычный запрос списка каналов включает эти поля и `unread_count`.

## Комментарии

Комментарий отправляется обычным POST сообщения с `reply_to_message_id` поста или
комментария того же канала. Backend вычисляет неизменный `thread_root_id` исходного
поста. Вложенные ответы остаются в одном обсуждении. Нельзя подставить пост другого
канала или создать корневую публикацию без прав автора. Реакции доступны и на постах,
и на комментариях по тем же ACL.

`GET .../messages/{messageID}/comments?before_id=...&limit=...` возвращает страницу
обсуждения корневого поста, с обычной `pagination`, в порядке от старых к новым.
Список сообщений и начальный sync-снимок показывают корневые публикации; дельты sync,
поиск и контекст сохраняют комментарии. `thread_root_id` и `comment_count` передаются
в HTTP и message-событиях. Счётчик комментариев обновляет revision исходного поста
и журнал sync; при создании/удалении комментария публикуется обновлённый пост.

Отключение комментариев запрещает новые ответы даже авторам/администраторам,
сохраняя чтение истории, реакции, редактирование/удаление собственных комментариев
и модерацию. Удаление поста каскадно удаляет обсуждение. Повторы отправки используют
существующие idempotency keys и не создают дополнительных комментариев/уведомлений.

Frontend показывает группу «Новостные каналы» над текстовой и голосовой группами.
Она существует только при наличии хотя бы одного **доступного** новостного канала
выбранного сервера. Недоступный закрытый канал не раскрывается даже наличием группы.
В обсуждение переходят кнопкой под публикацией; читателю основной ленты не показывают
поле публикации. Настройки авторов/комментариев находятся рядом с обычной приватностью.

## Непрочитанные уведомления

Новые подходящие уведомления сохраняются в `channel_notifications`, в том числе
для офлайн-аккаунтов. История до миграции не воспроизводится и не увеличивает счётчик.
Один message/user/channel учитывается один раз. Сохраняется текущая семантика:
исключены свои сообщения, muted-каналы, недоступные каналы и повторные отправки;
режим `mentions` учитывает упоминания и ответы пользователю; пересланный текст
не порождает упоминания.

Для обычного текстового канала по умолчанию `mentions`, для новостного — `all`.
Комментарии новостного канала уведомляют только упомянутых участников/получателей
ответа, чтобы обсуждение не отправляло уведомления всем подписчикам ленты.

```http
GET /api/v1/servers/{serverID}/notification-counts
```

```json
[{"channel_id":5,"unread_count":3},{"channel_id":7,"unread_count":0}]
```

Endpoint проверяет членство и возвращает только доступные каналы. Ответы настроек
и счётчиков имеют `Cache-Control: no-store`. Счётчик использует общий account/channel
read cursor, уменьшается при чтении с любого устройства и при удалении сообщения.
Триггеры убирают прочитанные строки; FK очищают данные при удалении сообщения,
канала или членства. Доставка сохраняется перед отправкой live-превью, но после
коммита сообщения: авария процесса между этими двумя действиями пока может
пропустить уведомление. Атомарный outbox — возможное последующее усиление гарантии.

На фронтенде числовой бейдж показывает до `99+`, с полным числом в title/accessible
названии. Точка непрочитанных сообщений остаётся для активности без отдельного
уведомления. Счётчики перечитываются пакетно при уведомлениях, read-событиях,
возврате фокуса и восстановлении sync. Изменение счётчиков не перезагружает ACL,
список участников или голосовые сессии. После переключения сервера начальный
список каналов восстанавливает актуальные значения.

## Откат

Откат 26 удаляет счётчики уведомлений. Откат 25 удаляет комментарии и назначения
авторов, сохраняя публикации как текстовые сообщения. Поэтому перед откатом нужна
резервная копия: содержимое обсуждений не восстанавливается одним повторным upgrade.

Проверки: backend-тесты прав, приватности, пересылки, nested replies, пагинации,
идемпотентности, каскадов и офлайн-счётчиков; браузерные сценарии группы каналов,
read-only ленты/комментариев, очистки бейджа и мобильного отображения.

Локальная проверка: `go test ./...`, `go vet ./...`, отдельный тест отката и
повторного применения миграций; 267 frontend-тестов, 36 браузерных сценариев,
TypeScript, ESLint и production-сборка. Race detector на этом Windows-окружении
не выполнялся: `CGO_ENABLED=0`, C-компилятор отсутствует. Его запуск остаётся
за существующим Linux CI с `go test -race ./...`.
