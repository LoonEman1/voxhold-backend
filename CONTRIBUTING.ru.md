# Разработка Voxhold backend

Все изменения, включая изменения владельца репозитория, проходят одинаковый
процесс:

```text
issue или задача → отдельная ветка → pull request → успешный CI → merge
```

Не разрабатывайте напрямую в `main` и не выполняйте merge, пока хотя бы одна
обязательная проверка ожидает запуска, завершилась ошибкой или была отменена.

## Процесс разработки

1. Обновите локальный `main` и создайте отдельную ветку:

   ```bash
   git switch main
   git pull --ff-only
   git switch -c feat/short-description
   ```

2. Сделайте одно сфокусированное изменение. Если меняется поведение или процесс
   эксплуатации, добавьте или обновите тесты и документацию.
3. Выполните локальные проверки:

   ```bash
   go test ./...
   go vet ./...
   ```

4. Создайте коммит, отправьте ветку и откройте pull request в `main`.
5. Дождитесь успеха всех обязательных проверок GitHub Actions. Исправляйте
   ошибки в той же ветке и ожидайте результат нового запуска.
6. Проверьте итоговый diff и выполняйте merge только при зелёном CI. Для
   сфокусированного PR предпочтителен squash merge; после merge удалите ветку.

Рекомендуемые префиксы веток: `feat/`, `fix/`, `docs/`, `refactor/`, `test/`,
`chore/` и `security/`.

CI намеренно разделён по типам событий:

- pull request запускает Go-проверки и валидирует `linux/amd64` без публикации,
  SBOM и provenance;
- push результата merge в `main` запускает только Go-проверки и не пересобирает
  образ;
- SemVer-тег запускает Go-проверки, публикует `linux/amd64` и `linux/arm64` с
  SBOM и provenance, а затем создаёт GitHub Release.

## Checklist для pull request

- изменение имеет понятную цель и не содержит посторонних правок;
- новое или исправленное поведение по возможности покрыто тестами;
- `go test ./...` и `go vet ./...` проходят;
- публичное поведение, конфигурация и deployment-изменения описаны на русском и
  английском языках;
- в коммитах отсутствуют пароли, `.env`, базы данных, логи с секретами и личные
  пользовательские данные;
- PR направлен в `main` и не сливается до успешного завершения CI.

Об уязвимостях следует сообщать по инструкции [SECURITY.md](SECURITY.md), а не
через публичный PR до согласованного раскрытия.

## Релизы

Voxhold backend использует теги Semantic Versioning:

- `v0.1.1` — обратно совместимое исправление;
- `v0.2.0` — обратно совместимая возможность на стадии `0.x`;
- `v1.0.0` — первый стабильный контракт API;
- `v0.2.0-rc.1` — предварительный релиз.

Релизный тег должен указывать на проверенный коммит, уже влитый в `main`.
Опубликованный тег нельзя перемещать или использовать повторно. Создайте
аннотированный тег и отправьте его:

```bash
git switch main
git pull --ff-only
git tag -a v0.1.1 -m "Voxhold backend v0.1.1"
git push origin v0.1.1
```

Workflow тега сначала запускает тесты, затем публикует мультиплатформенный образ
в GHCR и создаёт GitHub Release с автоматически сформированным описанием.
Стабильный `v0.1.1` создаёт теги образа `0.1.1`, `0.1` и `latest`; pre-release
не заменяет стабильный образ `latest`.

Перед сменой версии развёрнутого backend прочитайте описание релиза, создайте
резервную копию и укажите соответствующую точную версию:

```bash
./backup.sh
./update.sh --backend-version 0.1.1
```
